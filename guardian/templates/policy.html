Policy Editor

Edit file access, exec, and network policies per agent. Changes are saved to the config file on disk.

File Access Policy

Controls which files the agent can read/write. Deny rules always override allow rules.

Pattern syntax:
/tmp/**          # Everything under /tmp/
/etc/hosts       # Exact file match
/home/user/*.log # Single-level wildcard
Example allow list (default: deny):
/tmp/**
/proc/**
/usr/lib/**
/home/user/project/**
Example deny list:
/etc/shadow
/home/user/.ssh/**
/home/user/.aws/**
/home/user/.gnupg/**
Symlink bypass warning

If a parent folder is in allow and a subfolder is in deny, an agent can bypass the deny by creating a symlink from an allowed path (like /tmp/) to the denied folder. eBPF sees the raw path, not the resolved target.

Mitigation: Don't allow broad parent directories that contain denied subfolders. Instead, allow only the specific subdirectories you need. For cgroup agents, Landlock provides inode-level protection but only for allow rules (not deny).

Safe pattern for denying subfolders:
# WRONG (symlink bypass possible):
allow = ["/home/user/**"]
deny  = ["/home/user/secret/**"]

# RIGHT (allow only what's needed):
allow = [
  "/home/user/projects/app1/**",
  "/home/user/projects/app2/**",
  "/home/user/.config/**",
]
# secret/ is not in allow list — blocked by default

Exec Policy

Controls which commands the agent can execute. Uses the same pattern syntax as file access.

Important: Binaries may exist at multiple paths!

On merged-usr systems (Fedora, Arch), /bin, /sbin, /usr/bin, /usr/sbin may all contain the same binary. When denying a command, list ALL known paths. Use which -a <cmd> to find them.

# Example: deny grep at ALL known paths
/usr/bin/grep
/bin/grep
/usr/sbin/grep
Allowlist approach (default: deny):
# Only allow specific tools
/usr/bin/git
/usr/bin/node
/usr/bin/python3
/bin/bash
Blocklist approach (default: allow):
# Block dangerous commands
/usr/bin/curl
/usr/bin/wget
/usr/bin/rm
/usr/bin/ssh
/usr/bin/scp
Tip:

With default: deny, allow the agent's own binary, a shell, and all needed tools.

Network Policy

Controls outbound TCP connections by port number. Enforced by eBPF LSM socket_connect hook + Landlock (kernel 6.7+).

Common ports:
80    # HTTP
443   # HTTPS
22    # SSH
5432  # PostgreSQL
3306  # MySQL
6379  # Redis
8080  # Dev server
Example (default: deny, allow specific):
Allow: 80, 443
# Agent can only make HTTP/HTTPS requests
Example (default: allow, block specific):
Deny: 22, 25, 3306, 5432
# Block SSH, SMTP, database ports
Enforcement layers (kernel 6.7+):
  • Landlock TCP connect (kernel 6.7+) — blocks outbound TCP at the kernel VFS layer. Inode-level, no bypass. This is the primary enforcement for cgroup agents.
  • eBPF socket_connect LSM (kernel 5.7+) — second layer. Logs and blocks independently. Returns -ECONNREFUSED.
UDP gap — known limitation:

Landlock and eBPF only filter TCP connect(). UDP sendto() without a prior connect() is not filtered by either layer. This means:

  • DNS over UDP (port 53) works — but so does UDP-based data exfiltration
  • An attacker could use sendto() to exfil data over raw UDP to any port
  • DNS tunneling (encoding data in DNS queries) is undetectable by Guardian Shell
  • Mitigation: Use network namespace isolation (OpenShell/container) for full UDP control, or restrict DNS to a local resolver

Configuring Policies for AI Coding Agents (Claude Code, Cursor, etc.)

AI coding agents access far more files than a typical script. They need their own runtime, config files, shell init, caches, and your project directory. With default: deny, you must explicitly allow every path the agent touches — including files you might not expect.

Typical allow list for Claude Code (cgroup agent):
# Project directory (read + write)
/home/user/projects/myapp/**

# Claude Code data and auth
/home/user/.claude/**
/home/user/.claude.json

# Node.js runtime (Claude Code runs on Node)
/home/user/.local/**

# Package manager caches
/home/user/.npm/**
/home/user/.cache/**

# Config files (git, mise, editors, etc.)
/home/user/.config/**

# Rust toolchain (if using Rust tools)
/home/user/.cargo/**
/home/user/.rustup/**

# System paths (dynamic linking, shell, etc.)
/tmp/**
/proc/**
/sys/**
/dev/**
/run/**
/usr/lib/**    /usr/lib64/**
/usr/libexec/** /usr/share/**
/usr/local/**   /usr/bin/**
/usr/sbin/**    /sbin/**
/lib/**         /lib64/**
/bin/**         /etc/**
/var/**
Read-only paths (shell init files):
# Shell startup files — needed when the
# agent spawns bash subprocesses
/home/user/.bashrc
/home/user/.bash_profile
/home/user/.bash_logout
/home/user/.profile
Deny list (sensitive files):
/etc/shadow
/etc/gshadow
/home/user/.ssh/**
/home/user/.aws/**
/home/user/.gnupg/**
Common gotchas:
  • .claude.json lives at the home root, not inside .claude/ — must be allowed separately
  • .config/** is needed broadly (git, editor configs) — don't restrict to just one subdir
  • If the agent runs from a watched parent session (e.g. Claude Code running inside another Claude Code), the parent agent's policy also applies to guardian-launch
  • Landlock blocks silently — there is no log when it denies access. Use strace (below) to debug

Configuring Policies for OpenClaw (Telegram / Multi-Channel AI Agent)

OpenClaw is a general-purpose AI agent with shell exec, file access, and network capabilities. It connects to 20+ messaging channels (Telegram, Slack, WhatsApp). With 60+ known CVEs and default-open posture, kernel-level enforcement is critical. The Landlock allow list is the security boundary — deny lists are bypassable via symlinks.

# Allow only what OpenClaw needs:

20, 21, 23, 389, 636
OpenClaw-specific gotchas:
  • ~/.openclaw-dev/ is needed for --dev mode, ~/.openclaw/ for production — allow only the one you use
  • pnpm downloads tools to ~/.local/share/pnpm/.tools/ — must be in allow list
  • Launch from the OpenClaw directory (cd ~/codebrahma/openclaw) — pnpm scans the CWD
  • Telegram API uses port 443 — do NOT add 443 to deny_ports
  • OpenClaw's system.run tool inherits all cgroup restrictions — this is the primary attack surface

Troubleshooting: Agent Won't Launch

When a cgroup agent fails to start with default: deny, it's usually because Landlock is blocking a file the agent needs. Landlock denials are silent — they don't appear in Guardian's logs. Use strace to find which files are being denied.

Step 1: Install strace
# Fedora / RHEL
sudo dnf install strace

# Debian / Ubuntu
sudo apt install strace
Step 2: Trace the agent without Guardian
# Run your agent under strace and log
# all file access syscalls:
strace -f -e trace=openat,open,access,stat \
  -o /tmp/agent_trace.log \
  /path/to/your/agent

# Example for Claude Code:
strace -f -e trace=openat,open,access,stat \
  -o /tmp/claude_trace.log \
  /home/user/.local/share/mise/installs\
/node/24.1.0/bin/claude --help
Step 3: Extract accessed paths
# Find all unique paths under /home/:
grep -oP '"/home/[^"]*"' /tmp/agent_trace.log \
  | sort -u

# Find all paths that got EACCES errors
# (these are the ones being blocked):
grep 'EACCES' /tmp/agent_trace.log \
  | grep -oP '"[^"]*"' | sort -u
Step 4: Add missing paths to allow list

Group the discovered paths by directory and add them as glob patterns:

# If strace shows access to:
#   /home/user/.config/git/config
#   /home/user/.config/mise/config.toml
# Add the parent directory:
/home/user/.config/**

# If strace shows a specific file:
#   /home/user/.claude.json
# Add the exact file path:
/home/user/.claude.json
Alternative: Use audit framework
# If strace is unavailable, Linux audit
# can capture Landlock denials:
sudo auditctl -a always,exit \
  -F arch=b64 -S openat \
  -F exit=-13 -k landlock

# Launch your agent, then search:
sudo ausearch -k landlock --raw \
  | aureport -f
Tip:

Start with a broad allow (e.g. /home/user/**), confirm the agent works, then use strace to find the actual paths it needs and narrow the allow list down. This is safer than guessing.
